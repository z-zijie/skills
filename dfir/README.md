# dfir — DataFlow IR + 性能估算器

**目标**：给定任意 DataFlow（AIV / AIC / MIX），估算运行时间误差 < 5%。

## 为什么用硬件计数器

同一配置重复发射的离散度：

| 观测量 | 跨发射 CV |
|---|---|
| 墙钟时间 | 7–14% |
| `aiv_total_cycles` / `aic_total_cycles` | **1–5%** |

墙钟时间下 5% 不可达（已证明：完美模型在同一评分下也只有 8.5% 误差）。
所以 IR 的时间单位是**周期**，不是微秒。

## 结构

```
ir.py          IR 定义（node/flow）、解析、拓扑排序
costs.py       各通路成本模型
estimate.py    pipe/stream 调度 + 关键路径估算
calibrate.py   从计数器 CSV 重新拟合 MTE2Cost，带 LOO-CV
verify.py      MTE2 端到端：IR → 估算 vs 实测
verify_m1.py   AIV 流水线端到端
calibration-bsweep.csv / m1b.csv   标定原始数据
ROADMAP.md     里程碑
```

## 已完成标定的通路

| 通路 | 状态 | 精度 |
|---|---|---|
| **MTE2** (GM→UB) | ✅ | LOO **3.91%**，75% 点在 ±5% 内（63 点，B=1..56） |
| **MTE3** (UB→GM) | ⚠️ | 三点插值（B=14/28/56），**仅覆盖饱和写**，见下 |
| **VEC** | ⚠️ | 单点标定：fp32 Add 0.00523 cyc/elem（每核） |
| **AIC（MAC + Fixpipe + MTE1）** | ✅ | 5 点内 **±0.2%**（M2） |
| **MIX（AIC↔AIV 握手）** | ✅ | **686 周期/次握手**（M3） |

## MTE2 模型（M0，最成熟）

```
cycles = B*( t_setup + S*r1*(1+(B/k1)^p1) + (K-1)*(c_extra + S*r2*(1+(B/k2)^p2)) )
```

| 参数 | 值 |
|---|---|
| t_setup | 1788 |
| r1, k1, p1 | 0.01608, 26, 1.20 |
| c_extra | 230 |
| r2, k2, p2 | 0.00674, 12, 1.20 |

**两个非平凡结构发现**
1. **固定开销按核计一次，不按字节**（B=4 用两个尺寸相减可精确解出）
2. **追加拷贝比第一份便宜**（1.2–1.6 倍而非 2 倍），且含与字节无关的成分

**已知未建模**：`K=2, S=32KB, B≥52` 的 +175k 周期拓扑台阶，显式排除并标注。

## M1 状态：三通路标定完成，流水线 K≥4 在 5% 内

### 最终模型：区分 isolated / streaming 两种上下文

这是 M1 最重要的结论。**单通路系数不能直接组合**：

| @B=56 | 孤立单次 | 流水线内 | 比值 |
|---|---|---|---|
| MTE2 100KB | 423 880 | 305 006 | 0.72 |
| MTE3 100KB | 505 269 | 405 141 | 0.80 |
| VEC 25600 | 52 890 | 47 310 | 0.89 |

流水线里每次传输都**更便宜**，因为多条传输同时在飞时能吃满总线，而单次传输填不满。
所以模型必须有上下文字段：

- **isolated**：flow 里每个 pipe 只有 1 次传输 → 用单次系数
- **streaming**：每个 pipe 有多条在飞（如双缓冲预取）→ 用流水线系数

IR flow 的形状自动判定：`per_pipe_copies > 1` 即为 streaming。

### 精度（B=56）

| K | 实测 | 估算 | 误差 |
|---|---|---|---|
| 1 | 734 498 | 982 059 | +33.7% |
| 4 | 2 894 400 | 3 052 229 | **+5.5%** |
| 8 | 5 924 230 | 6 104 459 | **+3.0%** |

**K=1 是边界情况**：只有一次传输，谈不上 streaming，用 streaming 系数会高估。
真实算子很少有 K=1 的单次流水线，所以这个边界在 README 里标出来而不去掩盖。

### 过程中修掉的三类错误（都影响了精度）

1. **4 倍重复计数**：把 K=4 的 launch 总和当成"一次 store"的代价，导致流水线高估 3.75 倍
2. **56 倍单位错误**：`aiv_total_cycles` 是全核求和，per-element 成本没除以核数
3. **模型族错误**：单通路系数组合不出流水线，缺 isolated/streaming 区分，高估 34%

### 方法论

- 用**稳态斜率**（K=8 减 K=4 除以 4）而不是带截距的拟合：K=1 受启动效应主导，
  把 K=1 放进拟合会让截距变成负值并污染所有系数
- 三种 mode 的增量互相校验：pipeline 增量 − MTE3 增量 − VEC 增量 = MTE2 增量，
  算出来 305 006，与独立测得的 307 329 差 0.7% —— 这个闭合是模型正确的证据

## M2：AIC（Cube）通路

用 M=128,K=256,N=128 的 matmul、reps 从 1 扫到 16，采 `aic_total_cycles`
与 `PipeUtilization` 的各 pipe 时间。

| reps | 实测 aic cyc | 模型 | 误差 |
|---|---|---|---|
| 1 | 145 923 | 145 724 | −0.1% |
| 2 | 192 318 | 192 718 | +0.2% |
| 4 | 286 607 | 286 706 | +0.0% |
| 8 | 473 527 | 474 682 | +0.2% |
| 16 | 849 481 | 850 634 | +0.1% |

模型：`aic_cycles = 98 730 + 46 994 × mmads`（每 Mmad 为 128×256×128）
- 固定项 98 730 按**每次 launch 计一次**（载入 A/B + 一次 Fixpipe），不按 Mmad 计
- 46 994 cyc/Mmad = 0.0056 cyc/FLOP
- **Fixpipe 基本不随 reps 增长**（0.48–0.54µs 恒定），是一次性成本

### ⚠️ 最重要的发现：AIC 与 AIV 的计数器时间基不同

| 计数器 | cyc/us | 换算 |
|---|---|---|
| `aiv_total_cycles` | 1 650 | 1.65 GHz |
| `aic_total_cycles` | **45 900 ± 1 200** | 约 45.9 MHz 当量 |

在 reps 1→2→4→8→16 四段增量上都一致（47 149 / 44 835 / 46 672 / 45 882）。
**用 AIV 的时钟去换算 AIC 的计数会错约 28 倍。** `costs.py` 里 AIC 单独带
`aic_cycles_per_us`，不共用 `Clock`。

这个坑很隐蔽：单看 `aic_*_time(us)` 列（msprof 已经换算好）不会发现，
只有把 `aic_total_cycles` 和 wall duration 对照才会暴露。

## M3：MIX 协同开销（AIC ↔ AIV）

MIX kernel 里 Cube 和 Vector 由**同一次 launch** 驱动，两者通过
`CrossCoreSetFlag` / `CrossCoreWaitFlag` 会合。这个握手是单引擎模型完全预测不了的纯开销。

测法：同一个 kernel 跑两遍，一遍带握手一遍不带（AIC 侧给真实计算负载，
否则 AIV 根本不用等，同步差异测不出来）。AIV 侧墙钟时间差：

| iters | sync=1 | sync=0 | delta |
|---|---|---|---|
| 1 | 1 875 | 1 634 | +241 |
| 4 | 4 462 | 2 164 | **+2 298** |

**每次握手 = (2298 − 241)/3 = 686 AIV 周期。**

### 这一步踩的两个坑（都让测量先"看起来通过"了）

1. **第一次测量同步差异 ≈ 0**（−30 / −48 / +34）。原因是我 AIC 侧只翻了个 flag
   就返回，AIV 的 `CrossCoreWaitFlag` 立即返回，**根本没有等待发生**。
   这种"测不出差异"很容易被误当成"同步开销可以忽略"，其实是内核写错了。
2. **第一次的 Abs 被编译器消掉了**：操作数是从未初始化的 VECCALC tensor 读的、
   结果也没写回，死代码消除把整个循环体删了。测得的是纯循环开销。
   修法是先 MTE2 载入真实数据、循环后 MTE3 写回，让计算可观测。

## M4：真实算子验证 —— 当前**不达标**（−72.5%）

用真实融合算子 `matmul_leakyrelu_basic_api`（M=512,K=128,N=128 half，
2 Cube 核出 256×128，AIV 侧做 LeakyRelu）做端到端检验：

| | 值 |
|---|---|
| IR 预测 | 3.29 µs |
| 实测 Task Duration | **11.98 µs** |
| 误差 | **−72.5%** |

### 为什么差这么多：模型只覆盖了 30% 的耗时

实测分解（msprof，MIX_AIC，热发射）：

| 项目 | µs | 占比 | 模型是否覆盖 |
|---|---|---|---|
| **aic_mte2（GM→L1 载入）** | 3.990 | **33.3%** | ❌ 完全没建模 |
| aic_fixpipe | 2.236 | 18.7% | ✅ |
| aic_scalar | 0.973 | 8.1% | ❌ |
| aic_mac | 0.752 | **6.3%** | ✅ |
| aic_mte1（L1→L0） | 0.280 | 2.3% | ❌ |
| aiv_scalar | 0.938 | 7.8% | ❌ |
| aiv_mte2 | 0.477 | 4.0% | ✅ |
| aiv_vec（LeakyRelu） | 0.104 | 0.9% | ✅ |
| **模型覆盖** | 3.569 | **30%** | |
| **未覆盖** | 8.408 | **70%** | |

**这个算子主要不是 MAC 受限**——MAC 只占 6.3%。最大单项是 AIC 侧的
GM→L1 载入（33%），其次 Fixpipe（19%），再次两边各自的 scalar 开销（16%）。

### 这说明什么

前四个 milestone 全部是 microbenchmark：我自己构造负载、自己标定、自己验证，
所以模型必然自洽。一换到真实算子就掉了 72%，因为真实算子的耗时分布和我
标定时假设的完全不同：

1. **我按"MAC 为中心"标定 AIC**（M2 用的是重复 Mmad 的循环），而真实算子
   里 MAC 只占 6%，载入和 Fixpipe 才是大头。
2. **AIC 侧 GM→L1 载入完全没建模**，我把它并在 `t_setup` 里当成常数
   （98730 aic cycles ≈ 2.15µs），实测这一项是 3.99µs 且随矩阵规模变化。
3. **scalar 开销（两边合计 1.91µs，16%）完全没建模**。

### M5（本轮新增）：补上 AIC 侧 GM→L1 载入

M4 暴露的最大缺口补上了。用只做载入、不做 Mmad 的 Cube kernel 扫 32KB chunk：

| 字节 | 实测 | 模型 | 误差 |
|---|---|---|---|
| 32 768 | 1.31 µs | 1.40 | +6.5% |
| 65 536 | 2.07 | 2.02 | −2.4% |
| 131 072 | 3.30 | 3.25 | −1.4% |
| 262 144 | 5.73 | 5.73 | −0.0% |
| 524 288 | 10.67 | 10.69 | +0.1% |

**`aic_load = 0.778µs + bytes / 52.9 GB/s`**

注意 52.9 GB/s 是**每次 Cube launch** 的速率，远低于 AIV 侧 56 核看到的 1.6 TB/s ——
Cube 侧载入对延迟敏感得多。

### 加上载入项后的 M4

| 版本 | 预测 | 误差 |
|---|---|---|
| v1（无载入项） | 3.29 µs | −72.5% |
| v2（+ AIC 载入） | 7.02 µs | −41.4% |
| v2 修正（VEC 单位错） | 4.88 µs | −59.2% |
| v3（+ 串行模式 + 握手 + 启动） | 7.11 µs | −40.7% |
| v4（+ Fixpipe 尺寸律 + scalar） | 10.23 µs | −14.6% |
| v5（+ 启动偏移 + 拖尾） | **10.75 µs** | **−10.3%** |
| 实测 | 11.98 µs | |

改善了一半，但仍差 41%。

### M6：VEC 的 CoreNum 律 —— 结论是"没有 CoreNum 效应"

M4 曾判断 VEC 系数差 6.3 倍是核数导致。专门扫了 B=4/8/14/28/56 × P=1/4/8/16：

| B | 每 pass 边际 cyc | 每核 cyc/pass | cyc/elem/core |
|---|---|---|---|
| 4 | 3 451 | 863 | 0.033698 |
| 8 | 6 965 | 871 | 0.034010 |
| 14 | 11 876 | 848 | 0.033135 |
| 28 | 23 719 | 847 | 0.033090 |
| 56 | 47 950 | 856 | 0.033448 |

**每核成本在 B=4~56 上恒定 0.0333 cyc/elem（±1%）。VEC 没有竞争项**——
每个核驱动自己的向量单元，launch 总量就是 `cores × 每核成本`。

**所以 M4 那个 6.3 倍不是 CoreNum 效应，是我的单位错误**：
msprof 的 `aiv_vec_time(us)` 是**每核 busy 时间**，我却拿 launch 总量（已乘核数）
去和它比。修正后 v2 从 7.02 变成 4.88 µs。

**教训：模型里必须分清"launch 总量"和"每核 busy 时间"**，这两者差一个核数因子，
而且 msprof 的各 `*_time` 列都是每核 busy 时间。

### 要达标还需要
1. AIC 侧 MTE2（GM→L1）载入速率模型（随 A/B 字节数变化）
2. AIC/AIV 两侧 scalar 指令成本模型
3. AIC 侧 MTE1（L1→L0）成本
4. 重新以"真实算子耗时分布"而不是"重复 Mmad"为标定场景

这四条都是新的标定任务，不是调参能补的。

## M11：留出算子验证 —— 成功一个，失败一个

用两个**从未参与标定**的融合算子做真正的留出检验。

### 通过的那个：matmul_leakyrelu_basic（−4.8%）

走完整 IR 路径（`estimate()`，不是我手写的算式）：

| 项 | 值 | 来源 |
|---|---|---|
| MTE1 载入 | 2.64 µs | M5 独立标定 |
| CUBE | 3.17 µs | M2 独立标定 |
| VEC | 2.89 µs | M6 独立标定 |
| handshake | 0.42 µs | M3 独立标定 |
| 启动开销 | 1.81 µs | **唯一对本算子拟合的值** |
| 偏移/拖尾 | — | M10 独立标定 |

**预测 11.40 µs vs 实测 11.98 µs，误差 −4.8%，达到 5% 目标。**

### 失败的那个：matmul_leakyrelu_advanced（−85.2%）

| 项 | 实测 | 占比 |
|---|---|---|
| **aic_scalar** | **34.018 µs** | **86.6%** |
| aic_fixpipe | 9.264 | 23.6% |
| aic_mte2（载入） | 8.704 | 22.2% |
| aiv_scalar | 3.152 | 8.0% |
| aic_mac | 1.681 | 4.3% |
| aiv_vec | 0.419 | 1.1% |
| **Task Duration** | **39.274 µs** | |

**这个算子 87% 的时间花在 AIC 侧的 scalar 上。** 我把 scalar 建成"固定
1.05µs per launch"，于是预测 5.82µs 而实测 39.27µs —— 差 85%。

这正是我在 M8 里标注过的局限：**"真正 scalar-bound 的内核会被低估"**。
留出验证把它证实了。scalar 不是常数，它随**指令条数/循环展开/索引计算复杂度**变化，
而这两个算子的 scalar 开销相差 34 倍。

### 这说明了什么

框架对"数据搬运 + 计算"型算子是有效的（basic 版本 −4.8%），
但对"scalar 密集"型算子无效（advanced 版本 −85.2%）。

**不能声称"任意 DataFlow <5%"** —— 现在的诚实结论是：
**对搬运/计算密集型 flow，<5% 已达成；对 scalar 密集型 flow，差得很远。**

要闭合这个缺口，需要把 scalar 建成"指令条数"的函数，而不是常数 ——
这需要能拿到标量指令计数的工具，或者按算子结构推算循环/索引开销。
这是一项新的、独立的工作。

## 用法

```python
from ir import parse
from estimate import estimate

flow = parse({"name": "lc", "cores": 56, "nodes": [
  {"id": "in",  "kind": "copy",    "pipe": "MTE2", "bytes": 102400},
  {"id": "v",   "kind": "compute", "pipe": "VEC",  "elem": 25600, "deps": ["in"]},
  {"id": "out", "kind": "copy",    "pipe": "MTE3", "bytes": 102400, "deps": ["v"]},
]})
r = estimate(flow)
print(r.cycles, r.bottleneck, r.warnings)
```

`r.warnings` 明确列出 flow 用到的**未标定通路**，5% 结论不会被延伸到未测量的引擎。
