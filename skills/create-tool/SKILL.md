# 造一个工具

一个工具是留在仓库里、把一个问题的答案变成一条命令的代码。它跑在冷启动的 shell 里，靠一行输出和一个 exit code 说话。**答案先于工具存在**：先去拿答案，再造工具。

问题可以是任何东西；方法不变，数据源现场找。完整样例 [`references/get_npu_arch.py`](references/get_npu_arch.py)，先读它，再动手。

## 什么时候值得造

判断式只有一条，而且是回头看出来的：同一笔成本，已经付过，还会再付。三种形状都命中它：

- **动作在重复。** 同一件事第三次出现：第一遍学，第二遍确认，第三遍就该是一条命令。
- **答案来得贵。** 搞明白它消耗了大量精力，这份认知不固化就会蒸发。做成工具，下次是重跑一条命令，不是重走一遍调研。
- **杠杆足够大。** 手工做又慢又容易错，一条命令又快又确定，对错写在 exit code 里。

不值得造的，直接写：一次性的成本不会再付；上游已经用一条命令给出要的口径，再包一层没有增量。工具被 shell 运行，不被 import。

## 1. 先拿答案，再写工具

从环境里采访答案，不从记忆里取。找到权威的上游来源，亲手把答案跑出来一次。

- **来源。** 优先第一方渠道：官方命令、运行时接口、上游自己的配置和源码。候选逐个跑 `--help` 和一次真实调用；输出没有文档，就读上游源码。
- **口径。** 默认输出打印哪个字符串是产品决定：大小写、分隔、版本号去留，单独拍板。生态惯用哪个形态就输出哪个。
- **分歧。** 拿第二个独立来源交叉验证；两源不一致时选惯用口径，把另一个作为字段暴露，而不是丢掉。验证用的依赖留在你自己的 shell，不进脚本。

没亲眼见过答案跑出来，就没有工具可写。

## 2. 把工具写成契约

单文件、stdlib-only、自包含；落点遵守仓库的工具目录约定，用户没给名字就用 get_/check_ 前缀；结构对照样例。

- **一行答案。** `python3 xxx.py` 打印口径值，exit 0；查不到就 stderr 一行 `错误: ...`，exit 1。宁可非零退出报告，也不把占位值冒充答案。
- **`--help`。** 它是产品文档：usage、说明、真实示例、前置条件。用户只读这一屏。
- **机器可读。** `--json` 输出全部字段；数据源是表格时加 `--field` 取任意原始字段。
- **依赖。** 对环境的每项依赖都在运行时发现，PATH 之外留兜底定位。
- **上游输出。** 按不可信输入处理：显式编码、有超时、解析防御格式漂移。
- **docstring。** 写清做什么、数据源、字段含义、前置条件。

用户可见的 traceback 即缺陷。

## 3. 交付前证明它能用

每个出口实测一遍：默认输出、`--help`、`--json`、`--field`、每个失败分支、exit code。再到冷启动的 shell 里复测一次，确认它不依赖你 source 过的环境。把每条路径的真实输出贴进给用户的回复：那是评审可以重跑的证据，不是要用户信任的转述。

没实测过的工具是草稿，不是交付物。
