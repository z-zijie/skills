# 诊断一个问题

把一条能变红的复现物，变成一条有**运行时证据**的根因结论：症状如何从**机制**里长出来，从分界点到症状全程在证据里走通。修复不在本 skill 范围内：先定位，后动手。

读代码产出的是假设，不是结论。写进报告的每个结论要么有运行时证据，要么明确标注"推断"。

## 输入

复现报告（reproduce 的产物），至少含：一条能独立跑红的命令、分界症状句、仍开放的怀疑面。缺就先回 reproduce——对错误的症状做诊断，锚死的是错误的方向。

## 安全

- 探针与捕获工件里的秘密先 `<REDACTED>` 再进报告。
- 在隔离副本上插桩（worktree、调试副本）；生产环境插桩要用户明示许可。

## 1. 排序假设

从复现报告的开放怀疑面出发，写下 3-5 个假设，按"最可能 × 最便宜验证"排序，**先给用户看再动手**：用户一句"上周刚改过 X"常常瞬间重排整个清单。用户不在，按自己的排序继续。

每个假设必须**可证伪**，写成预测：

> 如果 X 是因，那么改 Y 症状应消失；加重 Z，症状应更频繁。

写不出预测的是感觉，改写或丢弃。只带一个假设就动手是被本 skill 拦截的失败模式：第一个貌似合理的想法会锚住后面所有工作。

完成判据：3-5 个假设各带预测，已排序。

## 2. 逐个否决

一次一个变量；每个探针对应一个预测，结果要么否决假设、要么收窄它。每改一个变量，重跑红命令看症状是否如预测变化。手段按信息量/成本排序，优先切掉最大的怀疑面：

1. **差分。** 同一输入在怀疑的两个版本/两个配置各跑一轮；一侧红一侧绿时，这个差异本身就是定位。
2. **二分。** 症状出现在两个已知状态之间时，怀疑面对半切（`git bisect`、逐段禁用、逐层短路），每刀跑一次复现物。
3. **单断点。** 调试器/REPL 在分界点停一次，胜过十条日志。
4. **定向日志。** 打在能区分假设的边界上。
5. **对照参考实现。** 怀疑 API 语义、用法有出入时，找正确用法对照。

AscendC 域内症状优先唤起 cannbot-skills 的专业调试 skill，用它们的域内流程执行上述手段：精度超差 `ascendc-precision-debug`，运行时报错与错误码 `ascendc-runtime-debug`，卡死/崩溃/内存错误 `ascendc-crash-debug`；项目里没有，就 `npx skills add https://gitcode.com/cann/cannbot-skills.git --skill <对应名>` 装上再用。

**插桩打标**：每轮探针用唯一前缀 `[DEBUG-xxxx]`，收尾一个 grep 全清。全量打日志再 grep 不在手段之列——分不开假设的日志是白噪声。

## 3. 性能症状分支

症状是"慢"而不是"错"时，日志几乎总是错的手段：先建**基线**再定位，手段见 [references/perf-baseline.md](references/perf-baseline.md)。基线建立之前，任何"优化建议"都不构成诊断。

## 4. 确认机制

幸存的假设升级为机制：症状如何从它长出来，在运行时证据里从分界点走通到症状。竞争假设全部否决或收窄到不构成解释。"看起来对"不算确认。

## 5. 落盘诊断报告

按 [references/diagnosis-report-template.md](references/diagnosis-report-template.md) 写报告并落盘，与复现报告同目录。报告面向下一个接手的人或 agent：读到它就能开始修复，无需重新诊断。

完成判据，逐项核对：

- [ ] 根因是一条机制，运行时证据从分界点走通到症状，证据是真实输出
- [ ] 竞争假设全部否决或收窄，每个附否决证据
- [ ] `[DEBUG-` grep 为零
- [ ] 修复建议给出最小正当改动的落点，或写明"没有正确的接缝"（架构发现）
- [ ] 报告落盘，接手者凭它可开工

## 诊断不出

预算内试尽仍无法确认机制时，未定位是合法结果，按模板收尾：幸存假设及各自的证据强度、已否决清单、探针记录、需要用户提供的（更多捕获工件、报告环境访问、生产插桩许可）。

硬造一个"看起来像"的根因，比没有根因更糟：它锚死的是错误的修复。
