# 修复一个问题

把一条被证实的根因，变成一个**最小正当改动**，外加一个在修复之前就写好、先红后绿的回归测试。症状补丁不是修复：只有兜住合法状态的护栏才叫修复，掩盖症状的护栏不是。

## 输入

诊断报告（diagnose 的产物）。根因一目了然的小问题可以直接进入本 skill，从红测试开始；根因不明，先回 diagnose。

## 1. 选接缝

**接缝**是能像真实调用方那样打到症状路径的公共边界。写下这个接缝抓得住什么、漏掉什么，用户在场就确认一次。

- 优先复用复现物：reproduce 报告里"可转回归测试"的复现物，本来就是接缝上的红测试底稿。
- **正确的接缝不存在时，这本身就是发现**：架构不允许把这个 bug 锁住。如实记录，交付时作为架构问题披露；不写一个假信心的测试。

## 2. 写红测试

把最小复现转成接缝上的失败测试，跑一次，亲眼看它以**预期的原因**变红——别的原因红不算。

- 期望值来自独立来源：已知正确的字面量、手算样例、参考实现的输出。把被测代码的当前输出抄进断言，测试永远绿。
- **证明变异**：红若是靠改代码或夹具造出来的（对尚无复现的 bug，改好代码证明测试能抓），diff 对照原始副本证明变异真的落了，再信这个红。

完成判据：一条会红的测试在改动之前存在。

## 3. 最小正当改动

在根因处修——系统第一次走错的地方。

- 一次只修这一个根因；无关清理另开提交或不做。
- 改动膨胀（牵出第二层重构、范围明显超出根因）时停下来报告，等用户划界。
- **修不动是新证据**：红测试不转绿，说明根因错了或不止一个，带着证据回 diagnose；两个共享同一前提的修复先后失败时，把前提写下来直接测它。

AscendC 精度类根因的修复模式先查 `ascendc-precision-debug` 的模式卡，修复有效性以它指定的验证工具为准（cannbot-skills；项目里没有就 `npx skills add https://gitcode.com/cann/cannbot-skills.git --skill ascendc-precision-debug` 装上再用）。

## 4. 复跑与有序提交

- 未最小化的原始场景重跑一遍，也绿才算修完（正式的前后对证在 verify，这里只确认绿）。
- 回归测试落进仓库约定的测试位置；`[DEBUG-` 前缀 grep 清零；复现物按 reproduce 报告的处置建议执行完毕（该转的已转，该删的删）。
- 两个有序提交：红测试先落，修复后落——读历史的人能看到症状曾经是真的。提交说明写**被证实的假设**（机制一句话），下一个排查的人从这里开始。遵守仓库的提交与分支规范，用户没说就在当前分支。

## 宁可不留测试

测试路径昂贵、集成过重、或唯一可用的接缝太浅时，用最接近的可执行检查代替（定向脚本、重放命令、日志断言），交付时说明为什么没有回归测试。**宁可没有测试，不留坏测试**。坏测试的形状：断言实现细节（重构即碎）、测的是 mock 不是行为、依赖时序或全局状态、为小修搭大型基建、证明完就该删的。

完成判据，逐项核对：

- [ ] 红测试先于修复存在，以预期原因变红，期望值独立
- [ ] 改动落在根因处，最小且正当，无关改动零混入
- [ ] 红测试转绿；原始场景重跑也绿
- [ ] 回归测试落位，或"宁可不留"的情形已写明
- [ ] `[DEBUG-` grep 为零，复现物处置完毕
- [ ] 两个有序提交，修复提交说明含被证实的假设
