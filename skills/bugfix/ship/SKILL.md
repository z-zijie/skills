# 落盘交付一个修复

把 reproduce、diagnose、fix、verify 四段的产物收拢成可评审、可追溯的交付物：干净的树、有序的提交、证据齐全的 PR。交付不合并：合并是评审者的事。

## 1. 清场

- `[DEBUG-` 前缀 grep 为零，诊断与修复两段的插桩一并清。
- 临时复现物按 reproduce 报告的处置建议执行完毕：该转回归测试的已转，确认即删的已删。
- 树里没有与本修复无关的改动；有就剥离出去，不搭车。

## 2. 核对有序提交

- 红测试提交在修复提交之前——读历史的人能看到症状曾经是真的。顺序不对就 rebase 修正。
- 修复提交说明含**被证实的假设**（机制一句话）；没有就补上——这是下一个人排查的起点。
- 遵守仓库的提交与分支规范。

## 3. 写 PR

按 [references/pr-template.md](references/pr-template.md) 写 PR 描述，六段齐全：

- **Why**：症状句（从复现报告抄）+ 问题标识。
- **根因**：被证实的假设，一段话机制。
- **修复**：改了什么，为什么最小。
- **证据**：before/after 真实粘贴、回归测试结果、影响面结论（等级标注）。
- **门**：one-way / two-way + 一句话影响面。
- **验证命令**：评审者可原样重跑的一条命令。

逻辑或流程改动，Why 里附一个**最小视觉**——伪代码、调用树或浅文件树：比一段散文更快被评审者看懂。

精度类结论的证据是验证工具的机读输出，不是转述（`ascendc-precision-debug`，cannbot-skills；项目里没有就 `npx skills add https://gitcode.com/cann/cannbot-skills.git --skill ascendc-precision-debug` 装上再用）。

PR 与提交里无秘密、无内部路径泄漏；现场工件先 `<REDACTED>` 再进证据。

## 4. 复盘钩子

交付后自问一次：这次诊断或修复里有没有值得固化的——复现物形态、插桩手段、接缝选择、踩过的坑？有就向用户提议固化（改 skill、建工具、补检查）。同一教训第二次出现时，必须固化。

完成判据，逐项核对：

- [ ] `[DEBUG-` grep 为零，复现物处置完毕，树里无搭车改动
- [ ] 红测试提交先于修复提交，修复提交说明含被证实的假设
- [ ] PR 六段齐全，before/after 是真实粘贴
- [ ] 评审者凭 PR 里的验证命令可独立重跑
- [ ] 复盘钩子问过：有提议，或确认无
