# 证明一个修复

"编译通过"不是证据，"单测绿"也不是：作者检查的是自己想建的东西。本 skill 产出**前后对证**——基线上症状在、修复版上症状消，各两遍——外加影响面检查与数字体检。验证不改代码：发现回归退回 fix。

## 1. 固定基线

基线是修复前的版本：PR 的 base、修复提交的父提交，或用户的报告环境。基线与修复版在隔离副本上分别跑，环境、数据、口径一致，唯一差异是那个修复。

**基线上症状跑不出来 = 没有基线**：一切"修好了"都无从谈起。如实报告，按复现报告的环境差异表回 reproduce 补条件。

## 2. 前后对证

沿未最小化的原始场景跑两遍：

| | 基线 | 修复版 |
| --- | --- | --- |
| 第一遍 | 症状在 | 症状消，正确终态出现 |
| 第二遍（重置后） | 仍在 | 仍消 |

两遍之间重置能影响症状的状态——与 reproduce 的独立确认同一条纪律。对拍口径按改动类型选，期望值独立（同 fix 红测试的纪律）：

| 改动类型 | 对拍方式 |
| --- | --- |
| 数值/精度 | 与参考实现或手算期望对拍，不是自比 |
| 性能 | 前后同口径 profiling/计时对比 |
| 行为/流程 | 走真实入口重放，不只跑单测 |
| 数据落盘 | 读回写入值核对 |

AscendC 精度类对拍走 `ascendc-precision-debug` 的验证工具与容差口径，判定取机读输出（cannbot-skills；项目里没有就 `npx skills add https://gitcode.com/cann/cannbot-skills.git --skill ascendc-precision-debug` 装上再用）。

## 3. 影响面

列改动能碰到的别处，重点放 grep 看不见的：跨模块读同一份数据、并发时序、相邻的状态/输入/权限/失败路径。

对大多数怀疑，找到**那个唯一的安全事实**——它成立，一批怀疑一次清空——并用运行代码证明它，不靠论述。每项怀疑标注确定性等级，报告写明停在哪一级：

1. 口说（无证据）
2. 指到行（file:line）
3. 推演排除
4. 代码证明
5. 真实场景复现

等级 1-2 的怀疑项进不了交付里"安全"的理由。

## 4. 数字体检

改动声称加速、减速时，数字过 [references/benchmark-vetting.md](references/benchmark-vetting.md) 的七问再进交付。结论四选一：更快 / 更慢 / 无可测差异 / 不可下结论。

## 5. 结局与独立性

结局只有四种，如实写：**verified**（基线红两遍 + 修复版绿两遍 + 影响面清零或已证明）/ **not-fixed**（修复版症状仍在——退回 fix，这是根因错误的新证据）/ **inconclusive**（某一半测不了，写明缺哪半）/ **无基线**。

作者自检不算终审：验证命令冷启动重跑一遍，重要修复交给没参与修复的执行者（子代理或用户）复跑。

完成判据，逐项核对：

- [ ] 基线红两遍、修复版绿两遍，重置动作写明
- [ ] 对拍口径匹配改动类型，期望值独立
- [ ] 唯一安全事实已证明（注明等级），剩余怀疑逐项标注等级与去留
- [ ] 性能数字过七问，或已标"不可下结论"
- [ ] 结局是四种之一，验证命令冷启动可重跑
- [ ] 证据与报告无秘密
